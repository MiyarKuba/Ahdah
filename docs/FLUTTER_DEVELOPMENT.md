# Flutter development

## Scope

The Flutter client targets Android, iOS, and Web. It implements startup/session verification, company onboarding, a responsive authenticated shell, role-aware navigation, manager invitation administration, manager join-request review, and a shared account/session page. Existing-member management, identity proofing, projects, financial workflows, dashboards, notifications, and offline transaction queues remain deferred.

## Architecture

The client under `frontend/ahdah_app/lib` is feature first:

- `app`: bootstrap, providers, Material 3 theme, routes, and guards.
- `core`: configuration, ProblemDetails/error mapping, localization mappings, Dio transport, token storage, preferences, validation, and shared responsive widgets.
- `features`: authentication, company registration, public invitation acceptance/join request, onboarding result, authoritative session state, authenticated shell/home/account, and manager access administration.
- `l10n`: Arabic and English ARB resources generated by Flutter `gen-l10n`.

Riverpod is used without code generation. `SessionController` is the single authoritative session state with `bootstrapping`, `unauthenticated`, `authenticated`, `temporarilyUnavailable`, and `sessionExpired` states. `go_router` guards use that server-verified state, never the presence of a token alone.

Manager access administration uses a focused `AccessRepository` and manually parsed immutable models. Invitation and join-request lists have separate Riverpod controllers for filter/pagination state. Invitation creation/cancellation and join approval/rejection each have focused write controllers. Duplicate page loads and submissions are suppressed, filter changes reset to page 1, pages deduplicate by stable resource ID, and loading-more failures preserve existing data.

## API configuration

The API's development HTTP port is `5231`, discovered from `backend/src/Ahdah.Api/Properties/launchSettings.json`. Every run/build requires:

```text
--dart-define=API_BASE_URL=<url>
```

`AppConfig` trims trailing slashes, requires an absolute HTTP(S) origin, rejects credentials/query/fragment components, and shows a developer-facing configuration page when the value is missing or invalid. There is no production fallback. Non-loopback release origins must use HTTPS; production deployments must always use HTTPS.

Addresses:

- Flutter Web: `http://localhost:5231`
- Android emulator: `http://10.0.2.2:5231`
- iOS simulator: `http://localhost:5231`
- Physical device: `http://<DEVELOPMENT_PC_LAN_IP>:5231` for local debug only; never commit a private LAN address. Prefer local HTTPS where available.

## Browser development and CORS

Run Flutter Web on the fixed port `5173`. The API's named `FlutterClient` CORS policy reads `Cors:AllowedOrigins`. Development explicitly contains `http://localhost:5173` and `http://127.0.0.1:5173`. It does not allow wildcard origins or credentials, and production must supply explicit HTTPS origins.

```powershell
cd C:\dev\Ahdah\frontend\ahdah_app
C:\dev\flutter\bin\flutter.bat run -d chrome --web-port 5173 --dart-define=API_BASE_URL=http://localhost:5231
```

## Platform networking

Android's main manifest contains only the normal Internet permission. A debug-only network-security configuration permits cleartext for emulator/LAN development and calls out `10.0.2.2`; no cleartext flag or configuration is merged into release builds. Build debug without launching an emulator:

```powershell
C:\dev\flutter\bin\flutter.bat build apk --debug --dart-define=API_BASE_URL=http://10.0.2.2:5231
```

This Android debug APK build passed. Gradle 9.1.0 downloaded successfully, and the first build installed the required NDK, Android SDK platforms, and CMake. The APK is at `frontend/ahdah_app/build/app/outputs/flutter-apk/app-debug.apk`. The app was not run on an emulator or physical device.

iOS uses the narrow ATS `NSAllowsLocalNetworking` setting, not `NSAllowsArbitraryLoads`. iOS remains unbuilt on Windows; compilation, signing, CocoaPods resolution, simulator testing, and device verification require macOS and Xcode.

## Token and session security

- Android/iOS: `flutter_secure_storage` persists the access token in platform secure storage.
- Web: `WebAccessTokenStore` holds the token only in a Dart object. It never uses localStorage, sessionStorage, IndexedDB, cookies, or SharedPreferences. Refreshing the page requires login again by design.
- SharedPreferences stores only the selected `ar`/`en` locale.
- Passwords and invitation tokens remain in form controllers only and are cleared after sensitive submissions and disposal. They are never persisted or logged.
- Dio adds `Authorization: Bearer` only when an endpoint explicitly requests authentication and a non-empty token exists. Body logging and automatic write retries are not configured.
- Startup does not make a separate health request. A stored mobile token is checked with `GET /api/v1/auth/me`. HTTP 401 clears it; network/timeouts retain it and show Retry.
- There is no refresh-token endpoint. Local logout deletes the access token and clears the in-memory user/company; it does not claim server revocation.
- Any authenticated access call returning 401 invokes `SessionController.expire`, clears the local token, and returns to login. A 403 does not clear a valid token. Network and timeout failures keep a potentially valid mobile token and provide retry.
- Raw invitation creation tokens remain only in the one-time result dialog's local call stack. They never enter Riverpod state, list records, routes, secure storage, preferences, browser storage, diagnostics, or logs. Closing the dialog drops the local reference and refreshes the list.

## Routes and guards

Named routes are `/`, `/welcome`, `/login`, `/register-company`, `/join-request`, `/accept-invitation`, `/pending`, `/home`, `/access/invitations`, `/access/join-requests`, `/account`, and `/unavailable`. The four authenticated destinations share one `ShellRoute`. Bootstrapping remains on splash, authenticated users are redirected away from onboarding to home, and unauthenticated shell access redirects to welcome. Invitation tokens and passwords never appear in paths, query parameters, or typed results.

`RoleCapabilities` maps the authoritative role from `/auth/me` to client capabilities. `Manager` receives Home, Invitations, Join Requests, and Account. Deputy, Accountant, Supervisor, Worker, and unknown future roles receive Home and Account. Manager pages are also protected by redirect logic, so hiding destinations is not the only guard. Backend authorization remains authoritative.

## Localization and presentation

Arabic is the default unless the user previously chose English. `flutter_localizations` and `gen-l10n` generate complete RTL/LTR resources from ARB files. Centralized mappings translate backend role, user/company status, and identity-status values; unknown future values use a safe localized fallback. The shared authentication shell is SafeArea-based, scrollable for keyboards, centered and width-constrained for tablet/Web, and remains usable on narrow screens.

The authenticated shell uses `NavigationBar` below 840 logical pixels and `NavigationRail` at 840 pixels and above. The app bar shows safe company and user context. Feature content is width-constrained, browser URLs/back navigation remain owned by `go_router`, and the same invitation/join/account widgets render across mobile, tablet, and Web.

Invitation and join-request APIs use page numbers beginning at 1, a UI page size of 20, exact lifecycle filters, and server-supplied `totalPages`. UTC ISO-8601 values are parsed defensively and displayed in the device local timezone with locale-aware Material date/time formatting. No page sweep is performed to calculate totals.

The account page displays safe `/auth/me` name, company, localized role, user status, and identity-verification status. The backend safe user summary now includes `identityVerificationStatus`; this was the only API contract correction and required no database change.
